# 熵管理（Entropy Management）

> 目标：让系统"保持整洁"——通过机制控制系统熵增速度，确保长期可维护。
>
> **本项目当前为人工门禁模式**：仓库内没有 CI 流水线、没有 git hook、没有单元测试、没有 Makefile。所有质量约束依赖开发者与 Agent 自觉执行，加上人工评审。本文如实描述现状，并把自动化门禁列为待建项（§2.3）。

## 1. 文档园艺机制

### 1.1 一致性检测项

| 检测项 | 当前频率 | 方式 | 状态 |
|-------|---------|------|------|
| `README.md` 与代码结构是否匹配 | 模块变更时 | 人工核对 | 手工触发 |
| Harness 文档与代码是否匹配 | 按需 | 人工扫描 | 手工触发 |
| Swagger 产物与 controller 注解是否同步 | 每次改接口 | `swag init` 后检查 `git status` | 人工 |
| `glossary.md` 是否覆盖新概念 | 引入新概念时 | 人工核对 | 手工触发 |
| 错误码 `msg` 映射是否完整 | 新增错误码时 | 人工核对 | 手工触发 |

### 1.2 园艺流程

1. 发现文档与代码不一致（路径失效、描述过时等）
2. 确定性问题（路径失效、命令错误）→ Agent 直接修复并提交
3. 判断性问题（描述与语义不符）→ 列出方案请人确认后修复
4. 复杂偏差（涉及产品语义变化）→ 转为缺陷或需求处理

### 1.3 文档更新纳入评审

改代码时若命中以下任一条，必须核查对应文档是否同步：

| 代码变更 | 应同步的文档 |
|---------|------------|
| `router/` / `controller/` 接口变更 | Swagger 注解（`swag init`）、`README.md` §API 接口 |
| 新增/删除目录或调整分层 | `AGENTS.md` 目录树、`docs/harness/architectural-constraints.md` §1.3 |
| 新增错误码 | `common/code/code.go`、必要时 `docs/glossary.md` |
| 引入新概念或缩写 | `docs/glossary.md` |
| RAG 方案变化 | `RAG详细设计.md` |

## 2. 违规检测与门禁

### 2.1 当前可用的检测手段

| 检测类型 | 触发时机 | 命令 | 阻断级别 |
|---------|---------|------|---------|
| Go 编译 | 本地 | `go build ./...` | 自我阻断 |
| Go 静态检查 | 本地 | `go vet ./...` | 自我阻断 |
| 代码格式 | 本地 | `gofmt -w .` | 自我阻断 |
| Swagger 一致性 | 本地 | `swag init` 后 `git status` | 自我阻断 |
| 前端启动 | 本地 | `npm run serve` | 自我阻断 |
| 代码评审 | 提交 | 人工 | 人工阻断 |

"自我阻断"含义：没有系统会替 Agent 拦截，**Agent 必须自己跑、自己看结果、自己修**。跳过验证直接宣称完成属于严重违规，见 [execution-verification.md](execution-verification.md) §2。

### 2.2 违规处理级别

- **阻断级别**（必须修复才能提交）：编译失败、生成产物未同步、架构规则 ARCH-001～ARCH-005 违规、密钥入库
- **警告级别**（可提交，记入技术债）：ARCH-006～ARCH-010 的合理例外
- **报告级别**（仅记录）：TODO/FIXME 新增、死代码

### 2.3 待建的自动化门禁

以下为当前缺失、建议补齐的能力，Agent 不得假设它们已经存在：

| 待建项 | 说明 | 优先级 |
|-------|------|-------|
| 单元测试 | 当前 `*_test.go` 为 0 个，核心逻辑（错误码、消息转换、工厂）无测试覆盖 | 高 |
| CI 流水线 | 仓库内无任何 CI 配置，提交无自动检查 | 高 |
| Makefile | 无统一命令入口，`go build` / `swag init` / 前端命令散落 | 中 |
| pre-commit hook | 无 husky / lint-staged，格式问题只能靠人发现 | 中 |
| `.gitignore` 核查 | 确认 `uploads/`、日志、临时文件已排除 | 中 |
| 架构规则自动化检查 | ARCH-001～ARCH-010 目前全靠人工评审 | 中 |

## 3. 技术债追踪

### 3.1 追踪机制

| 债务类型 | 识别方式 | 记录位置 | 清理策略 |
|---------|---------|---------|---------|
| 过时文档 | 人工扫描 | 本文 §3.2 | 发现即修复 |
| 未完成迁移（mock / 占位路径） | 代码搜索 `mock`、`TODO`、`占位` | 本文 §3.2 | 随对应需求一并清理 |
| TODO/FIXME | 代码扫描 | 代码内 | 每迭代 Review |

### 3.2 已知技术债清单（截至 2026-08-26）

| 项 | 描述 |
|----|------|
| 无单元测试 | 全仓库 0 个 `*_test.go`，核心业务（会话、RAG、工厂）无测试保护 |
| 无 CI / Makefile | 见 §2.3 |
| `num1.go` 学习文件 | 单例模式示例，非业务代码，建议移除或移入独立学习目录 |
| `utils/` 命名偏泛 | `utils.go` 职责较杂（MD5/UUID/消息转换/文件校验），可考虑按职责拆分 |
| 消息转换集中在 utils | `ConvertToSchemaMessages` 与业务耦合，后续可下沉到 `common/aihelper` |

### 3.3 技术债预算

| 规则 | 阈值 |
|------|------|
| 文档偏差 | 发现即修复，不积压 |
| 新增代码的技术债 | 必须在提交说明中写明原因和计划清理时间 |
| 新增架构例外 | 每次提交 ≤ 1 个，且必须在代码注释中写明原因 |

## 4. 熵增度量

| 指标 | 计算方式 | 阈值 | 超标动作 |
|------|---------|------|---------|
| 文档一致性 | 人工扫描发现的确定性问题数 | = 0 | 立即修复 |
| 已知技术债条目 | §3.2 清单条数 | 增长可控 | 排入迭代集中清理 |
| 编译可运行性 | `go build ./...` 通过 | 100% | 阻断新代码合入 |
| 测试覆盖 | `*_test.go` 数量 | 持续增长 | 见 §2.3 待建项 |
