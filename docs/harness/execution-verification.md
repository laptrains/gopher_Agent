# 执行与验证（Execution & Verification）

> 目标：让 Agent "做对事"——通过执行循环和强制验证确保任务被正确完成。
>
> 本项目**没有 CI 兜底**（见 [entropy-management.md](entropy-management.md) §2）。验证不是"跑一遍看看"，而是 Agent 声明完成前的强制前置条件。

## 1. 执行循环

### 1.1 循环结构

```text
while 任务未完成:
    1. 观察（Observe）— 读取相关代码与规范，确认当前状态
    2. 推理（Think）— 对照任务目标规划下一步
    3. 行动（Act）— 修改代码 / 调用工具
    4. 验证（Verify）— 执行 §2.1 中匹配的验证命令
    5. 更新（Update）— 更新任务状态与文档
```

### 1.2 循环保护

| 保护机制 | 配置 | 触发动作 |
|---------|------|---------|
| 最大修复尝试 | 同一验证失败连续 3 次 | 停止重试，向用户说明失败原因与已尝试方案 |
| 无进展检测 | 连续 3 次操作后状态无变化 | 暂停并请求人工介入 |
| 范围保护 | 修改文件数显著超出任务预期 | 暂停并确认范围 |
| 长耗时命令 | `npm install`、首次 `go run` 启动耗时较长 | 后台执行并轮询，不要反复中断重启 |

## 2. 强制验证机制

### 2.1 预完成检查清单

Agent 在宣称任务完成前，**必须**按变更类型逐项执行并确认通过：

| 变更类型 | 必须执行 | 说明 |
|---------|---------|------|
| 任意 Go 代码变更 | `go build ./...` | 编译通过是最低门槛 |
| 引入新 import / 依赖 | `go mod tidy`，随后 `go build ./...` | 确保 go.mod/go.sum 一致 |
| 格式化相关 | `gofmt -w .`（或 goimports） | 提交前统一格式 |
| 接口（controller/router）变更 | 更新 Swagger 注解 + `swag init` | 生成产物一并提交 |
| 新增错误码 | 检查 `common/code/code.go` 的 `msg` 映射已同步 | 每个 CodeXxx 都有对应消息 |
| 前端 `vue-frontend/**` 变更 | `npm run serve` 能正常启动（或 `npm run build` 通过） | 至少保证不报编译错误 |
| 数据模型 `model/**` 变更 | 确认 `common/mysql` 的 AutoMigrate 已覆盖 | 新增表/字段需在迁移列表中 |
| 任意变更 | 对照任务目标逐条核对 | 逐条，不是整体感觉 |
| 任意变更 | 对照 [architectural-constraints.md](architectural-constraints.md) §2.1 相关规则 | 没有 Linter 会替你检查 |
| 任意变更 | 对照 [entropy-management.md](entropy-management.md) §1.3 判断文档是否需同步 | |

**跳过条件**：只有当变更完全不涉及某一类文件时，才可跳过对应检查。"改动很小""应该没问题"不是跳过理由。

### 2.2 验证失败处理

1. 验证失败 → 回到执行循环定位并修复
2. 同一失败连续 3 次修复未果 → 停止，向用户说明：失败现象、已尝试的方案、判断的可能原因
3. **禁止**为了让验证通过而删除/跳过检查、注释掉断言、硬编码错误码

### 2.3 需人工确认的变更

以下变更 Agent 不得自行决定，须先获得确认：

- 分层结构或依赖规则调整
- 数据库表结构变更（新增字段/表/索引）
- 对外 API 的破坏性变更（删除字段、改语义、改路径）
- 引入新的第三方依赖
- 修改 `config.toml` 中的生产配置
- 修改既有错误码语义或移除错误码

## 3. 任务漂移检测

### 3.1 漂移信号与处理

| 信号 | 含义 | 处理 |
|------|------|------|
| 开始修改任务范围外的模块 | 范围蔓延 | 撤销无关变更，回到原任务；确有必要则先告知用户 |
| 自主更换技术方案 | 决策越权 | 暂停，说明原方案的问题并请求确认 |
| 反复执行同一操作无进展 | 陷入循环 | 终止，报告卡点 |
| 顺手"优化"了不相关代码 | 范围蔓延 | 撤销；改进建议写进总结而非直接改 |
| 为通过验证而弱化验证本身 | 严重违规 | 立即撤销，恢复原验证强度 |

### 3.2 范围边界

一次任务的修改范围应可用一句话描述。若无法一句话说清改了什么，说明范围已经失控，需要拆分。

## 4. 提交约定

### 4.1 分支

- 主分支：`main`（或团队约定的主分支）
- 特性分支：`feat/<topic>`
- 修复分支：`fix/<topic>`
- **禁止**直接向主分支推送

### 4.2 Commit message

- 建议附 conventional commits 类型（`feat` / `fix` / `chore` / `refactor` / `docs` / `test`）与作用域
- 描述用中文，说清"做了什么"而非"改了哪些文件"
- **仅在用户明确要求时才创建 commit**

示例：

```text
feat(session): 支持会话流式输出
fix(user): 修复验证码过期未校验的问题
docs(harness): 补充架构约束文档
```

## 5. 结果可观测性

### 5.1 Agent 执行记录

| 记录内容 | 位置 |
|---------|------|
| 任务状态与进度 | 会话内 todo 清单 |
| 运行时日志 | 本地 `go run` 的 stdout |

### 5.2 运行时排障入口

| 场景 | 入口 |
|------|------|
| 后端启动失败 | `go run main.go` 的 stdout 日志 |
| 接口连通性 | `GET /api/v1/...`、`GET /swagger/index.html` |
| RAG 向量索引 | `redis-cli FT.INFO rag_docs:*` |
| 消息落库异常 | RabbitMQ 管理控制台 |
| 前端启动失败 | `npm run serve` 输出 |

### 5.3 质量目标

| 指标 | 目标 |
|------|------|
| 提交前验证执行率 | 100%（对照 §2.1 匹配项） |
| 首次验证通过率 | 持续提升 |
| 因漏跑验证导致的返工 | 0 |
| 任务范围内变更占比 | 100%（无范围外改动） |
